客观地说： 这是三版里唯一一次真正的协议重构。问题在于——修完之后仍然留下了一条回退路径，以及一个语义写错的 sign。

02同时扩张的采集边界

新增权限

BLUETOOTH + BLUETOOTH_CONNECT

Android 12+ 的运行时权限，会弹窗——这是整个组件唯一一次必须向用户请求权限。

新增字段

PairedDevice / PairedMacAddress

上报用户连过的所有蓝牙设备：车机、手表、耳机、另一台手机。MAC 是硬件级唯一标识，可直接做社交关系图谱。

新增字段

SatelliteSupport / SatelliteEnabled

是否支持 / 开启卫星通信（天通、北斗短报文）。这是一个消费力分层指标，与“设备注册”毫无关系。

注册只需要 5 个字段（IMEI、ICCID、MNC、机型、制式）。4.0 采了 49 个。仅从“注册”这个业务目的出发，蓝牙配对设备与卫星开关都无法解释。

03TLS，以及它的后门

这是 4.0.0 最值得单独讲的一处：加上了 HTTPS，然后自己把门留着。

3.1 服务端证书是正规的

项值
subjectC=CN, ST=北京市, L=北京市, O=中国联合网络通信有限公司研究院, CN=dm.wo.com.cn
issuerCFCA OV RSA OCA G2（公共 CA，不是自签）
TLSTLSv1.3 / TLS_AES_256_GCM_SHA384

3.2 客户端的 TrustManager 却只验有效期

public void checkServerTrusted(X509Certificate[] chain, String authType) {
    if (chain == null || chain.length == 0) throw new CertificateException("服务端证书链为空");
    for (X509Certificate c : chain) c.checkValidity();   // ← 只看有效期，不 verify 签发者
}

没有 verify()、没有 pin。因此自签证书 + SAN=dm.wo.com.cn 即可完成中间人，客户端毫无察觉。

3.3 失败即降级

// e1/g.java
if (e instanceof SSLException) { ... }
// "HTTPS fail by cert invalid, trigger HTTP fallback!"  →  POST http://…:18080

配合上一条：中间人只要让握手失败（或直接篡改），整条链路就退回明文，body 与 sign 一起裸奔。企业 WiFi、校园网、公共热点、透明代理都具备这个条件。

结论： TLS 加上了，但可被任何能拦截握手的网络打回明文。“默认 TLS” 不等于 “实际 TLS”。

05自查与处置

# 版本
adb shell dumpsys package com.mobiletools.systemhelper | grep versionName
# 期望 4.0.0-20260910

# 权限（4.0 有 19 项，含 BLUETOOTH / BLUETOOTH_CONNECT）
adb shell dumpsys package com.mobiletools.systemhelper | grep -E "granted=true|BLUETOOTH"

# 是否在跑
adb shell ps -A | grep systemhelper
adb shell dumpsys alarm | grep systemhelper

# 撤新增的蓝牙权限
adb shell pm revoke com.mobiletools.systemhelper android.permission.BLUETOOTH_CONNECT

# 停用当前用户副本
adb shell pm disable-user --user 0 com.mobiletools.systemhelper
# 关键：4.0 必须同时封两个端口，光封 18080 不够
0.0.0.0 dm.wo.com.cn      # 一条域名规则即覆盖 :18080 与 :18081
为什么按域名封最稳： 两条通道同域不同端口，hosts / DNS 过滤在域名层一次性覆盖；而且它对平台签名组件同样生效，不依赖系统授权。
处置难度评估： 4.0 加了 signature 级权限保护，AIDL 拉起服务这条路被堵；但采集本体不受影响。停进程、撤权限、封域名仍然有效；彻底清除只能刷非定制固件。
